Prompts — el usuario decide cuándo se usan

Un prompt es una plantilla de mensajes con argumentos que el usuario invoca de forma explícita. El server la define; el host la muestra; el usuario decide cuándo arranca.

El usuario decide Sin efectos Argumentos tipados

Prompts · workflows

Plantillas que el server expone para una tarea concreta: revisar un PR, resumir un hilo, planificar un viaje. El usuario las elige desde la UI —normalmente como slash commands— y el server devuelve los mensajes ya armados.

Los argumentos son opcionales y declarativos. El host puede pedirlos, validarlos y autocompletarlos con la completion API antes de llamar a prompts/get.

El protocolo no impone la UI. Slash commands, menú, botón o atajo: el host decide cómo expone el catálogo de prompts del server.

El server devuelve mensajes completos, no una tool. El host los inyecta en el contexto y el modelo los usa como cualquier otro turno de la conversación.

El contraste con tools es de control, no de formato. Una tool la elige el modelo; un prompt lo elige el usuario. Si el usuario no lo invoca, el prompt no existe para el modelo, aunque el server lo tenga publicado.

El contenido lo escribe el server, pero el disparador es el usuario. Esa combinación es la que permite empaquetar workflows: el server sabe cómo se hace una revisión de código en su dominio y el usuario decide cuándo aplicarla.

La completion API no es obligatoria. Es una ayuda de UI: el host puede sugerir valores de argumentos consultando al server. Si no la implementas, el usuario escribe los argumentos a mano.
