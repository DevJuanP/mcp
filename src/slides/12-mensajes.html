Acto 3 · Arquitectura

Los tres tipos de mensaje

Todo el protocolo se reduce a tres sobres. Si entiendes cuándo hay id y quién responde, entiendes la mecánica completa.

Request id · espera respuesta

Lleva un id, un method y params. El receptor debe contestar con el mismo id.

request.jsonclient → server
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28"
    }
  }
}
Response mismo id · result o error

Devuelve el mismo id. Trae result o error, nunca los dos. Los resultados actuales incluyen resultType.

response.jsonserver → client
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "tools": ["…"]
  }
}
Notification sin id · nadie responde

No lleva id. Es un evento de un solo sentido: cambio de tools, progreso, cancelación. Nadie contesta.

notification.jsonserver → client
{
  "jsonrpc": "2.0",
  "method": "notifications/tools/list_changed",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/subscriptionId": 4
    }
  }
}
i En 2026-07-28 los servers no inician requests: los requests van del client al server y las responses al revés. Las notifications pueden fluir en ambos sentidos.

Simplifica: request = pregunta con número de ticket; response = respuesta con el mismo ticket; notification = aviso sin ticket. El id es lo que permite tener varias peticiones en vuelo sin mezclar respuestas.

La nota del pie es importante para quien leyó la spec vieja: en las versiones anteriores los servers podían iniciar requests (sampling, roots, elicitation). En 2026-07-28 eso se sustituye por el patrón de multi round-trip: el server devuelve input_required y el client reintenta.
