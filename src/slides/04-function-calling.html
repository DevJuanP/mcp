Acto 1 · El problema

Function calling no es MCP

Function calling resuelve una parte: que el modelo elija una función y sus argumentos. No resuelve cómo se descubre, se conecta y se autentica esa función en otra aplicación.

01 / USUARIO Pide el clima “¿Qué tiempo hace en Barcelona ahora mismo?”
02 / APP Arma la lista Nombre, descripción y schema de cada función disponible.
03 / MODELO Emite el JSON “Llama a weather_current con location=Barcelona”.
04 / APP Ejecuta Valida los argumentos, llama a la API y recoge el resultado.
05 / MODELO Redacta El resultado vuelve al contexto y el modelo responde.
Lo que function calling ya resuelveSuficiente para una app

El modelo elige qué función llamar y con qué argumentos a partir de una lista que la aplicación le pasa en el prompt. La app conserva el control de la ejecución.

Lo que no resuelveEl problema empieza aquí

Cómo descubre otra app esas funciones, con qué auth, con qué schema y por qué transporte. Cada app define su propio formato; no hay contrato entre apps.

! El modelo nunca ejecuta nada: propone una llamada. La app ejecuta. MCP estandariza esa parte de afuera —la conexión y el descubrimiento—, no la ejecución.

Si la audiencia viene de function calling, este es el punto exacto donde hay que distinguir las dos capas. Function calling es dentro de una app: el modelo elige entre las funciones que esa app le dio. MCP es entre apps y sistemas: cómo se descubre y se invoca una capacidad que vive en otro proceso.

La frase clave: el modelo propone; la app ejecuta. MCP no cambia eso. Lo que cambia es dónde vive la lista de funciones y cómo se obtiene.
