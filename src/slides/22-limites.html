Acto 6 · Seguridad y cierre

Qué NO resuelve MCP

Adoptar MCP tiene coste: un server que mantener, un contrato que versionar y una superficie de ataque nueva. La lista de límites es tan importante como la de beneficios.

✕ No gestiona el context window. El host decide qué entra, qué se resume y qué se descarta.
✕ No resuelve tu autorización. Define un framework de auth, no tu modelo de permisos.
✕ No define la lógica del agente. Planificar, iterar y decidir cuándo parar es de la app.
✕ No garantiza la calidad del dato. Si la API miente, la tool devuelve la mentira.
✕ No elimina el coste de mantener servers. Mueve la integración; no la borra.
✕ No es un API Gateway ni observabilidad. No sustituye WAF, cuotas, trazas ni métricas.

La pregunta honesta: ¿el coste de un server y su contrato se paga con el número de apps y sistemas que vas a conectar?

Árbol de decisión

dos preguntas · cuatro veredictos

¿Tienes muchas apps contra muchos sistemas?

¿Necesitas descubrimiento de capacidades en runtime?

Veredicto

MCP encaja: tienes un problema N×M y quieres descubrimiento en runtime. El coste del protocolo se paga solo.

El árbol no mide urgencia ni presupuesto. Si dudas, empieza por una API interna bien diseñada; MCP se añade cuando aparezca el segundo host.

Esta slide es el antídoto contra el hype. MCP es una buena decisión cuando hay multiplicación de integraciones o cuando quieres que hosts de terceros descubran tus capacidades. No es una buena decisión para una app con una sola API interna.

El árbol tiene cuatro salidas y ninguna es “MCP siempre”. La combinación más frecuente en empresas pequeñas es muchas apps, poco descubrimiento: ahí suele ganar una API interna con SDKs antes que un protocolo.

Si alguien pregunta por el coste: un server MCP es código de producción. Tiene tests, versiones, auth, errores, métricas y un contrato que puede romper a los hosts. Ese coste es real y hay que ponerlo en la balanza.
