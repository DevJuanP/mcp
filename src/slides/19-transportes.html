Los dos transportes

El mensaje JSON-RPC es idéntico; cambia cómo se enmarca y cómo viaja. stdio es un proceso local; Streamable HTTP es un endpoint remoto.

stdio local · subprocess

El host lanza el server como un proceso hijo y habla por sus streams estándar.

Hostclient
→
stdin / stdoutJSON por líneas
→
Serversubproceso
  • Un proceso por conexión. Si el proceso muere, la conexión muere.
  • Sin red. No hay TLS ni OAuth: las credenciales salen del entorno.
  • Framing por saltos de línea. Un objeto JSON por línea, sin logs en stdout.
  • Un client por proceso. El aislamiento es del sistema operativo.
Cuándo usarlo: filesystem, git, bases de datos locales, herramientas de escritorio y cualquier server que deba vivir en la máquina del usuario.
Streamable HTTP remoto · request-scoped

Cada mensaje es un POST a un único endpoint MCP. La respuesta llega como JSON o como un stream SSE ligado a esa request.

ClientPOST /mcp
→
Serverendpoint único
→
RespuestaJSON o SSE
  • Sin sesiones. No hay Mcp-Session-Id; cada POST es autosuficiente.
  • SSE por request. El stream vive lo que vive la petición, no la conexión.
  • OAuth 2.1 para remoto; headers Mcp-Method y Mcp-Name.
  • Sin reanudación. Si el stream se corta, el client reemite la request.
Cuándo usarlo: SaaS, multi-tenant, serverless, integraciones detrás de un API Gateway y cualquier server que muchos hosts deban alcanzar por red.
! HTTP+SSE está deprecado desde 2025-03-26 y sigue en la lista de deprecaciones. Si ves dos endpoints —uno para SSE y otro para mensajes— es la generación anterior. Migra a Streamable HTTP: un solo endpoint y un POST por mensaje.

La regla práctica: si el server corre en la máquina del usuario, stdio. Si corre en infraestructura compartida, Streamable HTTP. No hay un tercero activo.

stdio no es “menos seguro” por no tener OAuth. Es otro modelo de confianza: el usuario ya ejecutó el binario, así que el binario tiene sus permisos. La seguridad aquí es revisar qué instalas, no autenticar cada mensaje.

En Streamable HTTP, el detalle nuevo es que el SSE ya no es un canal global: es la respuesta de una request concreta. Eso elimina la reanudación con Last-Event-ID y simplifica el balanceo.

Si alguien menciona “SSE transport” como si fuera el estándar, está en 2024-11-05 o en 2025-03-26. La versión actual usa Streamable HTTP.
