server/discover request + response
request · client → server 
{
  "jsonrpc": "2.0",
  "id": "d-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
response · server → client 
{
  "jsonrpc": "2.0",
  "id": "d-1",
  "result": {
    "resultType": "complete",
    "supportedVersions": ["2026-07-28"],
    "capabilities": {
      "tools": {},
      "resources": {}
    },
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "weather",
        "version": "1.0.0"
      }
    }
  }
}
request 
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
response · resumida 
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "resultType": "complete",
    "tools": [
      {
        "name": "get_forecast",
        "title": "Weather Forecast",
        "inputSchema": {
          "type": "object",
          "properties": {
            "latitude": { "type": "number" },
            "longitude": { "type": "number" }
          },
          "required": ["latitude", "longitude"]
        }
      }
    ],
    "ttlMs": 300000,
    "cacheScope": "public"
  }
}
El modelo lee la lista y elige get_forecast con latitude: 41.39 y longitude: 2.17. Es una decisión del modelo dentro del host: en este paso no viaja ningún mensaje MCP.
No es MCP. El host construye el prompt con las tools que decide exponer. Si una tool no está en ese contexto, para el modelo no existe. El descubrimiento MCP no es descubrimiento del modelo: el host filtra y ordena.
request · el host ejecuta la intención del modelo 
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_forecast",
    "arguments": {
      "latitude": 41.39,
      "longitude": 2.17
    },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}
El argumento no viaja solo. El client valida el schema y el host puede pedir aprobación antes de enviar. La tool se ejecuta en el server, no en el modelo.
response · server → client 
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "resultType": "complete",
    "content": [
      {
        "type": "text",
        "text": "Barcelona: 24 °C, despejado. Mañana, 22 °C."
      }
    ]
  }
}
El resultado es contenido, no una verdad. El server devuelve texto estructurado; el host decide cuánto de eso entra en el contexto y cómo se presenta.
El host añade el resultado al contexto y el modelo redacta la respuesta final: «Mañana en Barcelona hará 22 °C y no hay alertas activas». El usuario la lee en la UI del host.
Tampoco es MCP. MCP termina en el resultado de la tool. Lo que el modelo haga con él —resumir, citar, combinar con otros datos— es responsabilidad del host.

Recorre los seis pasos con click. El objetivo no es memorizar los payloads: es ver dónde hay un mensaje MCP y dónde no. Los pasos 3 y 6 son los que más se confunden.

Paso 1: server/discover es obligatorio en el server, pero opcional para el client. Sirve para saber versiones y capacidades antes de pedir nada. En stdio también funciona como sonda de compatibilidad con clients legacy.

Paso 4: el host no “pasa” la llamada del modelo tal cual. Valida argumentos, aplica permisos y puede bloquear. La tool se ejecuta en el server.

Paso 5: el resultado vuelve como content. A partir de ahí, el host decide qué hacer con él. Esa frontera es la que separa el protocolo de la aplicación.
