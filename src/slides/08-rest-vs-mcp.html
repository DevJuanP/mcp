Acto 2 · La definición

API REST vs MCP

No compiten. REST expone resources y operaciones; MCP expone capacidades con semántica para un modelo. La diferencia que lo cambia todo es el descubrimiento en runtime.

Aspecto API REST MCP
Qué expone Resources y operaciones con verbos HTTP: GET /users/42. Capacidades: tools (acciones), resources (datos) y prompts (plantillas).
Quién consume Un desarrollador que lee la documentación y escribe código. Un host que descubre y negocia capacidades en runtime.
Contrato OpenAPI es opcional; la documentación puede ser prosa. inputSchema obligatorio por tool, en JSON Schema.
Descubrimiento Fuera de banda: docs, SDK, código escrito a mano. server/discover, tools/list, resources/list.
Transporte HTTP. stdio o Streamable HTTP. El mensaje JSON-RPC es el mismo.
Auth La que definas: API key, OAuth, mTLS, sesión. La implementa el server; OAuth 2.1 es la recomendación para remoto.
Versionado Por URL, header o media type. YYYY-MM-DD en cada request, dentro de _meta.
Comparten: HTTP, JSON, auth, versionado. Difieren: el contrato es machine-readable y el descubrimiento ocurre en runtime.
→ MCP no reemplaza tu API: la envuelve y la describe para que un modelo pueda descubrir qué puede hacer y con qué schema.

La comparación honesta: MCP y REST comparten la mitad del stack. La diferencia no es “mejor transporte” ni “mejor formato”. Es que MCP añade un contrato que un host puede leer sin que un humano escriba un client a medida.

REST te dice cómo pedir un resource; MCP le dice a un modelo qué capacidades existen y cómo invocarlas. Por eso el schema y el descubrimiento son la parte central, no el transporte.

Si alguien pregunta “¿entonces MCP es REST con JSON-RPC?”, la respuesta es: no exactamente. JSON-RPC es el formato de mensaje; la semántica de tools/resources/prompts y el ciclo de descubrimiento son lo que hace que sea MCP.
